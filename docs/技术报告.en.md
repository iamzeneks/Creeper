## 1. Project Positioning

Creeper is an encrypted steganography suite **disguised as a format-conversion program**: it encrypts arbitrary files and hides them inside PNG images, MP3 and WAV audio. The carrier plays back and displays as usual; only someone who knows the passphrase can recover the original.

It is not a safe — a safe tells others "there is something valuable here."
It is **daily life itself** — the secret sits in plain sight, but no one knows it is a secret.

## 2. Technology Stack

| Layer | Choice | Rationale |
|----|------|------|
| Language | C++17 (GCC 15.2 / w64devkit) | Single binary, no runtime, no performance compromise |
| Encryption | Windows **BCrypt (CNG)** — AES-256-GCM + PBKDF2 600,000 iterations | OS-level implementation, zero third-party dependency, industry standard |
| Image | **stb_image / stb_image_write** (public-domain single-header) | 20KB for the whole PNG ecosystem, lossless encode/decode |
| Audio | Hand-written MPEG frame parsing (sync word / frame length / auxiliary bits) | Pure byte operations, only touching 3 auxiliary bits in the frame header, no decoder needed |
| UI | **Dear ImGui + DirectX 11** | Modern dark UI, tens of KB of source for a complete interface |
| Chinese font | System Microsoft YaHei (loaded at runtime) | Zero packaging size, no missing glyphs on another machine |
| Portability | Static linking, only system DLLs | Copy to any Win10/11 and double-click to run |

**Selection philosophy: never reinvent the wheel when the OS provides it, never hand-write what's public-domain, hand-write only what must be hand-written (MPEG frame parsing, pure-software cryptography).**

## 3. Principles

### 3.1 The Math of Hiding: Redundancy in Carriers

Every digital file has "redundancy imperceptible to humans" — that is the physical basis of steganography.

```
PNG: pixel value ±1 (LSB matching) — a color shift of 1/255, invisible to the eye
     Embedding modifies only 1 bit in each of the RGB three channels, and only a random ±1 when the bit does not match the target (never forced to a value)
     After embedding, histogram pairing compensation is applied to non-carrying pixels, pulling the statistical distribution back to its original shape (L1 distance reduced by about 70×)
     Capacity = width × height × 3 ÷ 8 bytes (2560×1600 ≈ 1.46 MB), only 15% used by default (≈ 230 KB) to resist statistical detection

WAV: PCM sample LSB — depth bits per sample (default 1: only the lowest bit modified, ±1, LSB matching)
     Sample value shift of 1/32768 (16-bit, ≈ -90dBFS), inaudible; RIFF/fmt region and high bits untouched
     Capacity = sample count × depth ÷ 8 bytes (44.1kHz stereo per minute: depth=1 ≈ 661 KB, depth=2 ≈ 1.3 MB, depth=3 ≈ 1.98 MB),
     only 15% used by default (to resist statistical detection); `--depth 2|3` / GUI「位深」(bit depth) higher tiers double it stepwise (difference ≤3 ≈ -78dBFS, ≤7 ≈ -69dBFS, still inaudible)
     —— The largest capacity among the three carriers; the first choice for large files. WAV is lossless PCM, samples are raw data that can be rewritten directly; changing the lowest bit only touches the smallest magnitude of volume

MP3: MPEG frame-header auxiliary bits — 3 auxiliary bits per frame (private/copyright/original), 3 bits per frame
     The audio data region and the ID3 tag region are byte-for-byte untouched, the decode result is identical to the original file
     Capacity = frame count × 3 ÷ 8 bytes (19,194 frames ≈ 7.2 KB)
     —— MP3 is lossy compression: the data region is a Huffman-coded stream, changing any bit makes the decoded audio pop, so one can only modify
     the frame-header flag bits that the decoder never participates in computing ("not touching a single audio bit" is forced by the format, not a choice)
```

> Scheme evolution: initially PNG used forced LSB (change the lowest bit when it does not match), which left a step between adjacent bins H[2k]==H[2k+1] in the histogram; MP3 initially used the ID3v2 GEOB frame, which left a visible `creeper` filename and custom data in the tag region — both were features identifiable at a glance by sampling-based detection. The current scheme (±1 + histogram compensation / frame-header auxiliary bits) pushes the statistical footprint to the point of being indistinguishable from natural data. **Covertness is not "it looks unchanged" but "it is statistically unchanged."**

### 3.2 The Encryption Chain: Separating Content from Access

```
Payload file
  → zlib compression (minimize embedding size, reduce statistical exposure)
  → AES-256-GCM encryption (password → PBKDF2 600,000 iterations → key)
  → envelope (magic + random salt + nonce + ciphertext)
  → scattered into the carrier (PNG/WAV use a password-derived seed for pseudo-random placement; MP3 frame-order auxiliary bits XOR the password-derived keystream as a whole)
```

**Design point**: content security relies on AES, integrity on GCM authentication, brute-force resistance on PBKDF2 iterations — every layer is a standard answer, no homemade algorithm. Homemade cryptography is the mark of an amateur; Creeper does not do what amateurs do.

### 3.3 Existence Detection

Whether a carrier contains a payload **cannot be determined without decrypting**: the stego header has no fixed magic bytes (the PNG/WAV/MP3 bit streams all begin with "filename length" and carry no fixed feature; PNG/WAV scatter positions and the MP3 bit stream as a whole are password-derived, so with the wrong password even the header structure cannot be parsed). The only determination path is "fully parse with the password → GCM authentication" (false-positive probability 2^-128). To an external verifier, any file is "may or may not contain" — the existence question is locked away by the password itself. This is the mathematical form of "invisible without the password."

> Design trade-off: early versions used fixed magic bytes (`CRPR`/`CRP`) in exchange for O(1) detection, at the cost that **a verifier could find the payload in O(1) by pattern-matching the magic**. The no-magic rework (NO-MAGIC-1) raised the detection cost from "one string scan" to "one 600,000-iteration PBKDF2 + full parse," and reveals nothing when the password is wrong. `has` therefore changed from a "detection command" to a "password verification command" (`has <host> <password>`).

## 4. Operation Design

### 4.1 Three-Layer Disguise Structure

```
Layer 1: the program itself — a normal format converter (in appearance)
Layer 2: the interaction code — Ctrl+Shift+F summons a metadata edit window (only those who find the entrance know it)
Layer 3: the password field — "镜头格式" / "流派" (even the password box does not look like a password box: it defaults to a random fake format/genre name, and while typing each character is masked by random alphanumerics so bystanders only see random typing; the real input is stored bit-by-bit in an in-memory buffer, and a small grey ✕ at the right inside the input box clears it in one click)
```

### 4.2 Interaction Flow

```
Normal use (disguise layer):
  Add files → choose output format → Start Conversion → done
  (images are genuinely transcoded JPG↔PNG, survives hands-on verification)

Hidden use (real layer):
  Encrypt (single carrier): add 2 files (carrier first, payload last)
        → Ctrl+Shift+F → fill in password in 镜头格式/流派 → OK → Start Conversion
        (2 files = 1 carrier + 1 payload; embedded whether or not「硬件加速」is checked)
  Encrypt (multi-carrier sharding): add N+1 files (first N carriers, last one payload)
        → check「硬件加速」→ Ctrl+Shift+F → fill in password → OK → Start Conversion
  Decrypt (single carrier): add 1 file (a carrier with a payload)
        → Ctrl+Shift+F → fill in the same password → OK → Start Conversion → get the original
  Decrypt (multi-carrier merge): add all carriers (3 or more, order-independent)
        → uncheck「硬件加速」→ Ctrl+Shift+F → fill in the same password → OK → Start Conversion
```

#### 4.2.1 Sharding Protocol (Splitting Large Files Across Multiple Carriers)

A large file is first encrypted whole into a single AES-256-GCM envelope (`crypto_seal`, including DEFLATE compression), then the ciphertext is cut into chunks and hidden separately into multiple carriers. **Encrypt first, then split** is the key: any single chunk extracted is a meaningless ciphertext fragment; a single chunk cannot pass GCM authentication (the extract side treats it uniformly as "no payload"); all chunks must be collected and reassembled by sequence number before the whole can be authenticated and recovered — **single-carrier interception is meaningless.**

Each carrier's stego stream = standard stego header (name_len + name + env_len, with an extra 1-byte carrying depth before the rest in WAV) + env, where env is a shard chunk:

```
magic     4B  password-derived shard identifier = crypto_steg_seed(password, "creeper-split") (big-endian)
index     2B  big-endian, chunk sequence number (0..count-1)
count     2B  big-endian, total chunk count
chunk_len 4B  big-endian, length of this chunk's ciphertext fragment
chunk        ciphertext fragment
```

- magic is password-derived; static scanning finds no matchable feature; a wrong password makes magic mismatch → parsed as an ordinary envelope → GCM authentication fails → indistinguishable from "no payload"
- Capacity allocation: per-carrier availability = `floor(capacity × fill-rate) − header overhead`, filled sequentially from the head of the list (MP3 uses 100% — the frame-header auxiliary-bit scheme does not damage audio data, so there is no fill-rate concept)
- The chunk count / sequence number / total length fields are in plaintext — the exposure is only "other carriers exist," acceptable within a disguise-oriented threat model; if higher covertness is needed, the whole chunk header can be encrypted with a password-derived key (reserved evolution direction)

### 4.3 Design Discipline

- **UI copy never slips**: all errors are disguised as converter semantics ("转换失败：文件已损坏或格式不受支持"), the password/steganography concept is never exposed
- **Metadata window never really modifies files**: the password only goes into memory, EXIF/ID3 editing is a decoy, the carrier file has zero side effects
- **Low memorization cost**: one hotkey + one field, the mnemonic in one line: `Ctrl+Shift+F → fill password → OK → Convert`

## 5. Advantages

| Dimension | Creeper | Comparison target |
|------|---------|----------|
| **Lossless carrier** | Image color difference ≤1/255 with histogram compensation; audio byte-for-byte untouched outside the frame header | Most tools leave the file "dirty" after hiding |
| **Zero dependency** | 3 exes totaling 6.3MB, only system DLLs | Similar tools often bundle Python/OpenSSL |
| **Disguise depth** | Three-layer disguise, UI survives hands-on verification | Ordinary stego tools give away their purpose at a glance |
| **Cryptography** | Standard algorithms + strong KDF + authenticated encryption, cross-verified against Python cryptography | "Toy encryption" of homemade algorithms |
| **Portable** | Copy the folder and go, manual comes along | Requires installation and environment configuration |
| **Reverse-engineering cost** | No fixed magic bytes + exe string obfuscation; magic, fields, and flow all require reverse inference | Tools whose features are public become invalid on exposure |

## 6. Vision

### 7.1 What Works Now

| Scenario | Play |
|------|------|
| **Cloud privacy layer** | Hide sensitive documents in everyday photos/audio, drop into cloud drive/album/music sync — displays normally, only you know the content |
| **USB drive / portable disk** | Mix "carrying" WAV/MP3 into a music folder; even if the drive is borrowed, it goes unnoticed |
| **Social transmission** | Hide encrypted files in an image and send it over a normal chat channel, content is ciphertext throughout |
| **Personal archives** | Passwords, keys, scans of IDs, hidden in photo folders that family members browse |
| **Learning and research** | A complete hands-on practice of steganography, cryptography, and file formats (PNG/RIFF/ID3v2) |

### 7.2 Future Directions

- **Carrier expansion**: BMP (lossless LSB, same approach), JPEG domain (DCT coefficients + histogram preservation). Note: the WAV lossless LSB carrier landed on 2026-08-19 (PCM 8/16-bit, default 1 bit per sample, RIFF/fmt untouched, capacity ≈ 661 KB/min, default 15% cap); late on 2026-08-19, **configurable carrying depth** was added (`--depth 2|3` / GUI「位深」high 24bit / ultra 32bit → 2/3 bits per sample, capacity ×2/×3, difference ≤3 ≈ -78dBFS, ≤7 ≈ -69dBFS still inaudible; a 1-byte depth field added to the stego header; old-format files fall back to automatic parsing)
- **Covertness upgrade**: histogram compensation upgraded from "leveling after the fact" to "preserving throughout," payload sharding to resist detection (fragments scattered across multiple carriers, single-carrier interception meaningless). Note: "texture-adaptive embedding" (allocating capacity by pixel-neighborhood texture density) was evaluated, but a ±1 modification affects neighboring statistics by up to 2, and any content threshold leaves a fuzzy band that flips the mask so the extract side cannot replay the sequence — mathematically infeasible, abandoned; the current "pure password-derived scattering + 15% fill-rate cap + histogram self-adversarial re-embedding" covers the same protective intent
- **Form evolution**: from "three exes" to "one innocuous-looking album/player," the disguise layer blending into everyday software form
- **The philosophical endpoint**: when a tool resembles something enough, it disappears — only a code word remains between user and tool

### 7.3 The Honest Boundary

Creeper defends against "a casual look," not against "a targeted examination": the statistical deviation of a carrier at high fill rate is still measurable (chi-square/RS analysis), transcoding or compressing the carrier file destroys the data, and exe reverse engineering (XOR obfuscation only raises the cost, not irreversible). **±1 embedding + histogram pairing compensation + self-adversarial re-embedding have already pressed the footprint very low (measured L1 distance reduced by about 70×, no adjacent-bin step); the default 15% fill-rate cap keeps statistical exposure at a negligible level; scatter positions and the MP3 bit stream as a whole are password-derived (no plaintext magic bytes, no plaintext seed, no plaintext structure), so "whether a payload exists" is itself undeterminable — yet in principle there is no perfect steganography. It suits protecting privacy, not resisting professional forensics with a concrete subject of suspicion — this boundary is written in the manual and also here, because sobriety is part of the design.**
